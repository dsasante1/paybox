# Build a “paybox” — Local Payment Infrastructure Emulator

## Objective

Build a developer-focused local payment infrastructure emulator inspired by Floci.

The product should allow developers to run a complete, deterministic, local version of common payment-provider integrations without making real API calls or requiring access to provider sandbox environments.

The primary goal is:

> A developer should be able to point an existing application from Stripe, Paystack, Flutterwave, Kora, or another supported payment provider to a local endpoint and test realistic payment flows entirely on their machine.

The system should emulate the provider's API behavior closely enough that existing SDKs or applications can be configured to communicate with the emulator with minimal or no code changes.

The emulator must support:

* Payment initialization
* Payment authorization
* Payment confirmation
* Payment verification
* Payment capture
* Payment failure
* Payment cancellation
* Payment expiration
* Refunds
* Partial refunds
* Transfers/payouts
* Mobile-money payments
* Card payments
* Bank payments
* Virtual accounts where applicable
* Customers
* Payment methods
* Transactions
* Webhooks
* Webhook retries
* Idempotency
* Provider-specific response formats
* Provider-specific error formats
* Configurable latency
* Deterministic failure scenarios
* Dashboard for inspecting and controlling transactions
* CLI for scripting simulations
* REST API
* Persistent local storage
* Docker support
* Automated tests

# 1. Product Vision

The product should feel like:

```text
                    Payment Emulator
                          │
       ┌──────────────────┼──────────────────┐
       │                  │                  │
       ▼                  ▼                  ▼
    Stripe             Paystack          Flutterwave
    Adapter             Adapter             Adapter
       │                  │                  │
       └──────────────────┬──────────────────┘
                          │
                          ▼
                    Emulator Core
                          │
             ┌────────────┼────────────┐
             ▼            ▼            ▼
          Payments      Webhooks     Events
             │            │            │
             └────────────┼────────────┘
                          ▼
                    Local Database
```

The core engine should be provider-independent.

Provider adapters should translate between:

```text
Provider API
     ↓
Provider Adapter
     ↓
Canonical Payment Model
     ↓
Payment Engine
     ↓
Provider Adapter
     ↓
Provider API Response
```

This separation is extremely important.

Do NOT implement each provider as an independent application.

# 3. Provider Adapter Architecture

Create a provider interface.

Conceptually:

```typescript
interface PaymentProvider {
  initializePayment(input): Promise<ProviderPayment>;
  verifyPayment(reference): Promise<ProviderPayment>;
  authorizePayment(input): Promise<ProviderPayment>;
  capturePayment(input): Promise<ProviderPayment>;
  cancelPayment(input): Promise<ProviderPayment>;
  refundPayment(input): Promise<ProviderRefund>;
  createTransfer(input): Promise<ProviderTransfer>;
}
```

Provider adapters implement this interface.

Example:

```text
StripeAdapter
PaystackAdapter
FlutterwaveAdapter
KoraAdapter
```

However, provider-specific behavior must NOT be unnecessarily normalized away.

For example:

* Paystack has its own reference model
* Stripe has PaymentIntent/Charge concepts
* Flutterwave has its own transaction model
* Kora has its own transaction/payment models

The emulator should preserve provider-specific semantics at the API boundary while internally maintaining a canonical model.

# 7. Payment State Machine

Implement an explicit transaction state machine.

For example:

```text
created
   ↓
pending
   ↓
processing
   ├───────────────┐
   ▼               ▼
successful       failed
   │
   ▼
refunded
```

Some payments may follow:

```text
created
 ↓
requires_action
 ↓
authorized
 ↓
captured
 ↓
successful
```

Invalid transitions must be rejected.

For example:

```text
failed → successful
```

should not be allowed unless explicitly simulated as a provider reversal/retry event.

All state transitions must produce events.

# 29. Security

The emulator must be safe by design.

Important rules:

* Never process real payments.
* Never send real payment requests by default.
* Never require real provider credentials.
* Never store real card details.
* Never store CVV.
* Clearly label all generated credentials as TEST/LOCAL.
* Bind to localhost by default.
* Require explicit configuration to expose the server externally.
* Warn when binding to `0.0.0.0`.
* Prevent accidental production API calls.

The project is considered complete when a developer can:

1. Install the emulator locally.
2. Start it with one command.
3. Point an existing payment integration at localhost.
4. Initialize a payment.
5. See the payment in the dashboard.
6. Simulate success/failure.
7. Receive a provider-compatible webhook.
8. Verify the transaction.
9. Refund the transaction.
10. Inspect the complete transaction timeline.
11. Replay webhooks.
12. Simulate failures.

# 52. Implementation Instructions

Before writing code:

1. Inspect the repository.
2. Determine whether an existing architecture should be preserved.
3. Create an implementation plan.
4. Identify the smallest viable MVP.
5. Research the current official API documentation for each provider.
6. Do not rely on memory for provider-specific API behavior.
7. Clearly document any behavior that cannot be accurately emulated.
8. Design the canonical payment engine before implementing provider adapters.

Then implement incrementally.

After each major component:

```text
implement
→ test
→ inspect
→ fix
→ document
```

Do not create placeholder implementations that appear functional but do not actually model the payment lifecycle.

---

# 53. Quality Requirements

The resulting project must be:

* modular
* strongly typed
* testable
* deterministic
* extensible
* documented
* Docker-compatible
* secure by default
* provider-agnostic internally
* provider-compatible externally

Avoid:

* unnecessary abstractions
* premature microservices
* hard-coded provider responses
* duplicated business logic
* real payment credentials
* real payment processing
* provider-specific logic in the core engine

The system should initially run as a **single local application**.

Do not introduce distributed infrastructure unless it provides a clear benefit.

# Final Goal

The final product should feel like:

```text
                 YOUR APPLICATION
                       │
                       ▼
              ┌──────────────────┐
              │ Payment Emulator │
              │                  │
              │ Stripe           │
              │ Paystack         │
              │ Flutterwave      │
              │ Kora             │
              └────────┬─────────┘
                       │
             ┌─────────┴─────────┐
             │                   │
             ▼                   ▼
        Payment Engine       Webhook Engine
             │                   │
             ▼                   ▼
        Local Database       Your Webhook
             │
             ▼
          Dashboard
```

The key differentiator should be **realistic payment behavior rather than static mocks**.

A developer should be able to test the difficult parts of payment integration—pending transactions, asynchronous mobile-money authorization, duplicate webhooks, retries, timeouts, failed payments, refunds, idempotency and inconsistent network behavior—entirely on localhost.

Build the project with this principle:

> **“If my production payment integration can encounter it, I should be able to reproduce it locally.”**
