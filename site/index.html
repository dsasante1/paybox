paybox is a local payment infrastructure emulator. Point an existing Paystack, Stripe, Flutterwave, Kora, Quid Payments, WeWire or Wise integration at localhost and drive pending mobile-money authorization, webhook retries, duplicate deliveries, timeouts, refunds and idempotency — deterministically, offline.

$ npx paybox-emulator start
Getting started Read the source

Node 22.5 or newer is the only requirement — no clone, no database server, no compiler. Or docker run --rm -p 127.0.0.1:8080:8080 dsasante1/paybox.

Not a mock server

Every request drives a real state machine.

A charge appends to an append-only event log, moves through the same canonical statuses the organic flow would, and emits the same signed webhooks. The payment row is a projection of that log, which is why the timeline, webhook replay and audit trail are one mechanism rather than three.

No real money can move through this process. It has no code path that reaches a payment network, it refuses live API keys, it never stores a CVV, and it binds to 127.0.0.1 by default.

The interesting part

Fast-forward instead of waiting.

Time is virtual. The scheduler compares due jobs against the virtual clock and runs each one at the instant it was scheduled for, so one advance fires the whole window — a five-attempt retry ladder, or twelve monthly renewals with twelve correct dates.

paybox
# A mobile-money charge answers immediately; the customer has not approved yet.
$ paybox payment create --amount 25000 --method mobile_money --reference momo_1
  → requires_action, "Please approve the payment prompt on your phone"

# Fast-forward. Every job that comes due runs before this returns.
$ paybox time advance 5s
  → successful, charge.success delivered

# Make every webhook fail, then watch the retry ladder run to exhaustion.
$ paybox webhook fail http_500
$ paybox time advance 2h

# Replay a delivery with a byte-identical signed payload.
# Does your handler double-credit the customer?
$ paybox webhook replay whd_...

# Duplicate and reorder every webhook.
$ paybox webhook chaos --duplicate true --out-of-order true

# Hold the API response open so the webhook lands before the call returns.
$ paybox network latency 3000

What you get

The failure modes, on demand.

Virtual time

time advance 1y runs a year of scheduled work instantly — renewals, expiries and retries, each stamped at the moment it was due.

Deterministic runs

A fixed PAYBOX_SEED and a frozen clock reproduce a run byte for byte, so tests can assert on literal ids and exact timestamps.

Webhook chaos

Signed deliveries with real retry ladders, forced failures, duplicates, reordering and byte-identical replay.

Asynchronous authorization

Mobile-money prompts that sit in requires_action, PIN and OTP loops, and stored authorizations you can charge again.

Money movement

Refunds and partial refunds, disputes, transfers that reserve against a balance folded from an append-only ledger, subscriptions and invoices.

Idempotency and latency

Replayed keys answer from the stored response; injected latency lands on the response, so a webhook can beat the call that created it.

Dashboard and event stream

Five views over payments, webhooks, jobs and the log at /dashboard, with an OpenAPI reference at /docs.

CLI-driven, CI-ready

Every control is a command and an HTTP route, so a test can create, settle, fail, advance and assert without a browser.

Coverage

Seven providers, eight adapters — each partially implemented.

Partial means partial. Each contract page lists what is implemented, what differs from the real provider and what is absent. If something is missing from one, assume it is not there. Every adapter declares what it serves in a manifest, and a test fails if the manifest and the router disagree in either direction — so these counts cannot overstate what the emulator answers.

Zero to a simulated payment

Change a base URL. Nothing else.

paybox status prints the credentials each adapter issued. They are labelled test credentials that exist only in the local database.

.env
PAYSTACK_BASE_URL=http://127.0.0.1:8080/paystack
PAYSTACK_SECRET_KEY=sk_test_local_a1b2c3...

STRIPE_API_BASE=http://127.0.0.1:8080/stripe
FLW_BASE_URL=http://127.0.0.1:8080/flutterwave   # v3, FLWSECK_TEST-… keys
KORA_BASE_URL=http://127.0.0.1:8080/kora
then, exactly as you would against Paystack
$ curl -X POST http://127.0.0.1:8080/paystack/transaction/initialize \
    -H "Authorization: Bearer sk_test_local_a1b2c3..." \
    -H "content-type: application/json" \
    -d '{"email":"dev@example.com","amount":10000,"currency":"GHS","reference":"order_1"}'

{
  "status": true,
  "message": "Authorization URL created",
  "data": {
    "authorization_url": "http://127.0.0.1:8080/paystack/checkout/48zrdrkbqv7e",
    "access_code": "48zrdrkbqv7e",
    "reference": "order_1"
  }
}

That URL is a real checkout page with the test instruments listed on it. Add a webhook endpoint with paybox webhook add, run paybox payment success order_1, and your app receives a signed charge.success while verify starts answering "status": "success".
